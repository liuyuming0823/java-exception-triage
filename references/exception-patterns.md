# Java 异常诊断判定规则

本文件是技能执行时必须加载的硬性知识。核心是「证据驱动」——每条根因都要能回溯到堆栈里的具体一行，不能凭感觉下结论。

## 一、异常链解析顺序（必须先做）

Java 异常往往带 `Caused by` 链，真正的根因通常在**最内层**，不是打印在最上面那行。

- 从栈顶往下找最后一个 `Caused by`，那是根因帧。
- 最外层通常是框架的包装异常（如 `ServletException`、`UndeclaredThrowableException`），只告诉我们「在哪一层被兜住」，不直接告诉我们「为什么」。
- 解析顺序：① 最内层 `Caused by` 的异常类型与消息 → ② 该帧的出错类/方法/行号 → ③ 顺着栈向上看是谁调用了它。

## 二、三方框架帧 vs 业务帧

栈帧分两类，定位重点不同：

| 帧类型 | 特征 | 定位重点 |
|---|---|---|
| 三方框架帧 | 包名含 `org.springframework`、`com.sun`、`java.`、`com.fasterxml`、`org.apache`、`javax.` 等 | 多半是「用法错」或「配置错」，不是框架 bug |
| 业务帧 | 包名是用户自己的项目（如 `com.xxx.service`、`cn.xxx.dao`） | 问题最可能落在这里，优先圈定 |

规则：先标出第一个业务帧，它之上的三方帧是「传播路径」，之下的业务帧是「源头」。报告里用「问题很可能落在 [业务类.方法]」表述，不写成「一定是」。

## 三、常见异常类型 → 候选根因速查

| 异常 | 典型根因（待证据确认） | 最该看的帧 |
|---|---|---|
| `NullPointerException` | 对象未注入/未初始化、Mapper 返回 null 后直接调方法、Optional 未判空、自动拆箱 null | 第一个业务帧的行号 |
| `ClassNotFoundException` / `NoClassDefFoundError` | 依赖缺失、作用域 wrong、打包漏类、版本冲突 | 出错类全限定名 |
| `NoSuchMethodError` | 两版本 jar 冲突（编译时用 A，运行时加载 B） | 方法签名 + jar 版本 |
| `SQLException` / `BadSqlGrammarException` | SQL 写错、字段名错、MyBatis 占位符与参数不匹配 | Mapper 的 statement id + SQL |
| `SQLException: 违反唯一约束` | 重复插入、主键生成策略冲突、并发写 | 插入的表与字段 |
| `BeanCreationException` | 配置错、循环依赖、缺少 `@Bean`/`@Component` | 出错的 Bean 名 |
| `TransactionSystemException` | 事务超时、连接池耗尽、只读事务里写 | 事务管理器配置 |
| `StackOverflowError` | 无限递归、双向关联 JSON 序列化 | 重复出现的同一个方法 |
| `OutOfMemoryError: Java heap space` | 大对象、泄漏、集合无限增长 | 堆 dump 分析（非本技能范围） |
| `IllegalArgumentException: JSON` | 字段类型不匹配、日期格式错、枚举越界 | 出错的 DTO 字段 |

注意：上表是「方向」，不是「结论」。必须回到用户堆栈找对应证据，不能在没看到堆栈时直接套。

## 四、状态标签规范（本技能最硬的设计）

每条候选根因必须带状态标签，且标签含义固定：

- **【已证实】** —— 证据直接写在堆栈/代码里，不需运行即可确认。例如堆栈明确显示 `at com.xxx.OrderService.create(OrderService.java:42)` 且第 42 行是对一个 null 调用方法，则 NPE 根因为「OrderService 第 42 行对 null 调用」属已证实。
- **【待验证】** —— 需要跑一下、加日志、或看代码才能确认。例如「可能是连接池耗尽」但堆栈只有超时，看不到池指标，则标待验证，并给出验证步骤。

约束：不把「可能」写成「就是」；不输出没有任何对应证据的根因；验证未完成前，修复建议明确标注「未经验证，不要直接上生产」。

## 五、最小验证步骤写法

验证步骤要可执行、具体到动作，禁止写「检查一下配置」这类空话。合格写法示例：

- 在 `[类.方法]` 第 `[N]` 行前加日志，打印 `[变量]` 是否为 null。
- 在 IDE 对该方法入口打断点，触发一次请求，观察 `[参数]` 实际值。
- 执行 `mvn dependency:tree | grep [artifactId]` 看是否有多版本 jar。
- 打开 `application.yml`，核对 `[配置项]` 是否拼写/缩进正确。

## 六、异常来自三方包内部的三种可能

当根因帧落在三方包内部（非业务帧），必须区分：

1. **用法错误** —— 用户调用方式不对（参数、配置、版本不匹配）。最常见。
2. **版本不兼容** —— 用户代码针对旧版 API，运行时是新版，或反之。
3. **三方 bug** —— 确认是库自身缺陷。最少见，必须给出复现条件与 issue/版本号才敢下此结论。

默认先归「用法错误」，除非证据支持后两者。
